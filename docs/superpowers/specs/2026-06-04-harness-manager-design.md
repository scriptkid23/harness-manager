# Harness Manager — Design Spec

- **Date:** 2026-06-04
- **Status:** Approved (design), pending implementation plan
- **Author:** brainstorming session

## 1. Purpose

A **local-first control plane** for applying Harness Engineering practices (from the
*Learn Harness Engineering* course) across multiple repositories. It stores and surfaces
each repo's **agent definitions, feature list, progress, decisions, and sessions**, and
exposes an **MCP server** so coding agents (Cursor, Claude, Codex) can read and write that
harness state directly. **Langfuse** is used as the observability / trace store for agent
sessions.

### Core principle

The **repository is the single source of truth** (Lecture 3). Harness artifacts live as
git-tracked files in each repo under `.harness/`. The system's SQLite database is only an
**index/cache + cross-repo aggregation** that can be rebuilt at any time from the files.

## 2. Scope

- **In scope:** local-first, single user, runs on localhost, no complex auth.
- **Entities managed per repo:** agent definitions, feature list, progress, decisions,
  sessions (linked to Langfuse traces).
- **Out of scope (YAGNI for now):** multi-tenant SaaS, team auth, quality document
  (Lecture 12 quality scoring) — may be added later.

## 3. Architecture

Nx monorepo (TypeScript). Four packages:

```
harness-manager/
├── packages/
│   ├── core/   # Pure logic: Zod schemas, parse/serialize .harness/ files,
│   │           # generate AGENTS.md. No I/O side effects. Shared by mcp + api.
│   ├── mcp/    # MCP server (@modelcontextprotocol/sdk, stdio) embedded in
│   │           # Cursor/Claude. Reads/writes repo files via core; sends traces to Langfuse.
│   ├── api/    # HTTP service (Fastify) for the dashboard: register repos, on-demand
│   │           # re-index into SQLite, cross-repo queries. Also pushes Langfuse traces.
│   └── web/    # Dashboard (Next.js/React): view repos, features, progress, decisions,
│               # sessions; embed/link to Langfuse.
├── prisma/     # SQLite schema (cache + aggregation + session/trace links)
└── docs/
```

### Data flow

- **Agent (Cursor/Claude)** ⇄ **MCP server** ⇄ read/write **`.harness/` in repo**
  (canonical) → upsert into **SQLite** (cache) + send **trace → Langfuse**.
- **Dashboard (web)** ⇄ **API** ⇄ read SQLite + on-demand re-index from repo files;
  embed Langfuse to view traces.
- `core` is the shared layer (parse/validate/generate) so MCP and API never diverge.

SQLite is a rebuildable index. On conflict, the file wins.

## 4. Repo file layout (Approach A)

Each managed repo gets a `.harness/` directory plus an auto-generated `AGENTS.md`:

```
repo/
├── AGENTS.md                  # auto-gen: thin entry file (Lecture 4) — overview, commands,
│                              # hard constraints, links into .harness/. Contains marker
│                              # "<!-- generated by harness-manager -->" (do not hand-edit).
└── .harness/
    ├── config.json            # repo metadata: name, description, langfuse project, hard constraints
    ├── agents/
    │   ├── planner.md         # YAML frontmatter (id, role, model, tools) + body = instructions
    │   └── generator.md
    ├── features.json          # array of features: id, behavior, verification, state, evidence
    ├── progress.md            # frontmatter (current_commit, test_status, updated_at) + prose body
    └── decisions.md           # sequence of blocks, each frontmatter (id, date, title) + rationale
```

### Conventions

- **JSON for machine-read state** (`features.json`, `config.json`) → precise Zod parsing.
- **Markdown + frontmatter for prose** (`agents/*.md`, `progress.md`, `decisions.md`) →
  machine-readable head + human-readable body, nice git diffs.
- **`AGENTS.md` always auto-generated** from `.harness/` (keeps it a thin entry file per
  Lecture 4; never bloats).

### Schemas (Zod, in `core`)

```ts
// agent
{ id: string, role: string, model?: string, tools?: string[], instructions: string }

// feature (Lecture 8: behavior + verification + state)
{ id: string, behavior: string, verification: string,
  state: "not_started" | "active" | "blocked" | "passing", evidence?: string }

// progress (Lecture 5)
{ currentCommit?: string, testStatus?: string, updatedAt: string,
  completed: string[], inProgress: string[], blocked: string[], nextSteps: string[] }

// decision (Lecture 5)
{ id: string, date: string, title: string, rationale: string, rejected?: string }

// config
{ name: string, description?: string, langfuseProjectId?: string, hardConstraints: string[] }
```

## 5. MCP server & tools

MCP server runs over stdio, embedded in Cursor/Claude. It receives `repoPath` (current
workspace) to identify the repo. Each tool call manipulates `.harness/` files, upserts
SQLite, and writes one Langfuse span.

### Read / query tools

- `harness_init` — scaffold `.harness/` + `AGENTS.md` for a new repo.
- `harness_get_context` — landing page: overview, hard constraints, active agents, active
  feature, current progress, next steps. **Clock-in** tool (Lecture 5/6); starts a session.
- `harness_list_features` — features + state, filterable by state.
- `harness_list_decisions` — recent decisions.
- `harness_get_progress` — current progress.

### Write tools (write to repo files, then re-index)

- `harness_update_feature` — edit behavior/verification, or **propose** a state change.
  Cannot set `passing` directly.
- `harness_set_feature_passing` — only accepted with `evidence` (commit/log). Implements
  pass-state gating (Lecture 8).
- `harness_update_progress` — update completed/inProgress/blocked/nextSteps + commit/test
  status.
- `harness_add_decision` — add a decision (title + rationale + rejected alternative).
- `harness_upsert_agent` — create/edit an agent definition.
- `harness_handoff` — **clock-out** (Lecture 12): update progress, write a session record,
  end the trace, run a basic clean-state check (warn if progress stale / active feature
  unfinished).

### Harness principles embedded in tools (not just CRUD)

- **WIP=1 (Lecture 7):** `harness_update_feature` warns if a 2nd feature would go `active`.
- **Pass-state gating (Lecture 8):** only `set_feature_passing` reaches `passing`, and it
  requires evidence.
- Every write tool regenerates `AGENTS.md` so the entry file stays in sync.

## 6. Sync & Langfuse tracing

### Sync (on-demand, repo canonical)

- No file watcher/daemon. SQLite is cache/aggregation only.
- Each read of a repo: `core` reads `.harness/`, validates with Zod, then **upserts into
  SQLite** with a content hash. Always fresh because it always reads files.
- Dashboard has a **"Re-sync"** button (API re-reads all `.harness/` for a repo).
- MCP write tools: write file first (canonical) → upsert SQLite → file wins on mismatch.

### Repo registration

`repos` table: `{ id, name, path, langfuseProjectId }`. Users add a repo via the dashboard
(enter path) or it auto-registers on first `harness_init` / `harness_get_context`.

### Tracing (Lecture 11 — runtime observability)

- A **session** = one agent work session. Starts at `harness_get_context` (clock-in) →
  creates a Langfuse **trace** (id stored in `sessions`).
- Each subsequent MCP tool call = a **span** in that trace (tool name, input summary,
  result, duration).
- `harness_handoff` (clock-out) closes the trace and may attach a simple **score** (e.g.
  `clean_state`: pass/fail).
- `sessions` table: `{ id, repoId, langfuseTraceId, startedAt, endedAt, summary }`. Dashboard
  lists sessions + **links/embeds** the Langfuse UI for trace detail.
- Configured via env (`LANGFUSE_HOST`, public/secret key). Missing key → tracing is a
  silent no-op; the system still runs.

## 7. Dashboard (web) + API

### API (`packages/api`, Fastify)

Simple REST, localhost, no auth.

- `GET /repos`, `POST /repos` (register path), `POST /repos/:id/resync`
- `GET /repos/:id/context`
- `GET /repos/:id/features`, `GET /repos/:id/progress`, `GET /repos/:id/decisions`,
  `GET /repos/:id/agents`
- `GET /repos/:id/sessions` (with Langfuse trace link)
- Uses `core` for read/validate so it never diverges from MCP.

### Dashboard (`packages/web`, Next.js)

- **Repos page:** registered repos + add/re-sync, quick summary (features passing/total,
  open session?).
- **Repo detail** tabs:
  - *Overview* — rendered `AGENTS.md` + hard constraints + agent definitions.
  - *Features* — kanban by state (not_started / active / blocked / passing), behavior +
    verification + evidence.
  - *Progress* — completed / in-progress / blocked / next steps + commit & test status.
  - *Decisions* — timeline of decisions + rationale.
  - *Sessions* — list of sessions, each links/embeds Langfuse trace.
- Read-only primary (agents write via MCP; repo canonical). Has "re-sync" + open-file. The
  dashboard does not overwrite files (avoids source-of-truth conflicts).

## 8. Error handling

- **Validate at the boundary (Lecture 10):** every `.harness/` file is parsed via Zod.
  Corrupt/invalid file → clear error with path + bad field, **no crash**; SQLite keeps the
  old index.
- **Agent-oriented error messages (Lectures 9 & 10):** MCP tool errors include fix
  instructions, e.g. `"features.json: feature F03 missing 'verification'. Add a verification
  command then retry."`
- **Safe writes:** atomic write (temp file + rename) to avoid corruption mid-write; regen
  `AGENTS.md` after writing.
- **Langfuse fails silently:** missing key / Langfuse down → tracing no-op; system runs.
- **Missing/uninitialized repo path:** clear message + suggest `harness_init`.

## 9. Testing strategy

- **`core` (primary, unit):** round-trip parse↔serialize per artifact; stable `AGENTS.md`
  generation; Zod rejects bad input; pass-state gating & WIP=1 logic.
- **`mcp` (integration):** temp repo in test dir, call each tool, assert `.harness/` changes
  + SQLite matches. Mock Langfuse client.
- **`api` (integration):** endpoints with temp SQLite + repo fixture.
- **`web`:** light tests (key components + render from mock data). Avoid over-testing
  (Lecture 12: avoid harness bloat).
- **Minimal E2E (Lecture 10):** one full flow — init repo → get_context → update_feature →
  set_passing (with evidence) → handoff → verify files + session record.
